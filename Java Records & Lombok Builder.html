Java Record

Java Record — Immutable Data Carrier

A record is a compact way to define an immutable data carrier. Java automatically generates the canonical constructor, accessors, equals(), hashCode(), and toString().

Syntax

@Builder
public record User(
    String name,
    String email,
    int age
) {}
Key point: The record keyword tells Java to auto-generate all boilerplate — constructor, accessors, equals(), hashCode(), and toString().

Accessors

Record accessors use the component name directly — no get prefix:

User user = new User("John", "john@est.com", 20);

// Accessor calls (NOT getName(), getEmail())
user.name();    // "John"
user.email();   // "john@est.com"
user.age();     // 20

What's Auto-Generated

  • Canonical constructor (all parameters)
  • Accessor methods: component()
  • equals() and hashCode()
  • toString()
  • All component fields are final

Lombok @Builder

@Builder — Fluent Construction Pattern

@Builder generates a fluent Builder pattern, allowing readable, step-by-step object construction.

On a Class

@Builder
public class User {
    private String name;
    private String email;
    private int age;
}

On a Record

@Builder
public record User(
    String name,
    String email,
    int age
) {}

Usage (identical for both)

User user = User.builder()
    .name("John")
    .email("john@est.com")
    .age(20)
    .build();
Why use @Builder? When a constructor has many parameters (especially optional ones), the builder pattern provides readable construction code compared to long constructor argument lists or multiple setter calls.
Under the Hood

What @Builder Generates

Think of the builder as a temporary object that collects values. build() then creates the final object.

@Builder Pattern — Two-Phase Construction

Generated builder() Method

public static AuditPublishRequest.Builder
    builder() {
  return new AuditPublishRequest.Builder();
}

Generated build() Method

public AuditPublishRequest build() {
  return new AuditPublishRequest(
      eventKind, action, entity,
      entityId, summary, actor, changes
  );
}
Real-World Example

AuditPublishRequest — Record + @Builder

This combines a record for immutable data with @Builder for readable construction. A compact canonical constructor normalizes null changes into an empty immutable list.

@Builder
public record AuditPublishRequest(
    String eventKind,
    String action,
    String entity,
    String entityId,
    String summary,
    Actor actor,
    List<ChangeEntry> changes
) {
    public AuditPublishRequest {
        changes = changes == null ? List.of() : changes;
    }
}

Construction with Builder

AuditPublishRequest req = AuditPublishRequest.builder()
    .eventKind("USER_CREATED")
    .action("CREATE")
    .entity("User")
    .entityId("usr_123")
    .summary("New user registered")
    .actor(actor)
    .// changes omitted → null → normalized to List.of()
    .build();
Result: Null-safe by design — if changes is omitted, the compact constructor normalizes null → List.of() → []. This avoids null checks for all callers.
Compact Constructor

Compact Canonical Constructor

The compact constructor has no parameter list — it implicitly receives all record components. Its job is validation and normalization during construction.

Syntax

public record AuditPublishRequest(
    String eventKind,
    String action,
    List<ChangeEntry> changes
) {
    // Compact constructor — no params!
    public AuditPublishRequest {
        changes = changes == null
            ? List.of()
            : changes;
    }
}

What It Does

Null Normalization Flow
  • Runs before the object is fully constructed
  • Can validate input (throw on bad data)
  • Can normalize/transform values
  • No explicit parameter list needed

@Builder.Default

@Builder.Default — Respecting Field Initializers

By default, @Builder ignores field initializers. @Builder.Default tells Lombok to use the initializer as the default value when the builder caller does not specify that field.

Without @Builder.Default

@Builder
public class User {
    private String role = "USER";
}
// ⚠ builder().build() → role is null!
Problem: The builder's internal fields start at their Java defaults (null for objects), ignoring the = "USER" initializer.

With @Builder.Default

@Builder
public class User {
    @Builder.Default
    private String role = "USER";
}
// ✓ builder().build() → role is "USER"
Result: User.builder().build() produces a user with role = "USER" — the field initializer is respected.
toBuilder

@Builder(toBuilder = true) — Modified Copies

Useful for creating a modified copy of an immutable object. The toBuilder() method returns a builder pre-populated with the current object's values.

@Builder(toBuilder = true)
public record User(String name, int age) {}
toBuilder — Clone and Modify Pattern
// Usage
User user1 = User.builder().name("Alice").age(25).build();

User user2 = user1.toBuilder()
    .age(26)
    .build();
// user1 unchanged (immutable) — user2 has age=26
Design Decision

When Should You Use a Class?

Prefer a class when you need mutable state, setters, inheritance, significant behavior, or a typical JPA entity.

Class — Mutable with Behavior

public class Workflow {
    private WorkflowStatus status;

    public void approve() {
        this.status = WorkflowStatus.APPROVED;
        // trigger side effects, notifications...
    }

    public void reject(String reason) {
        this.status = WorkflowStatus.REJECTED;
        // log reason, notify...
    }

    public boolean isTerminal() {
        return status == WorkflowStatus.APPROVED
            || status == WorkflowStatus.REJECTED;
    }
}

Why Not a Record Here?

  • Mutability: Status changes over time — final fields won't work
  • Behavior: approve(), reject() encapsulate state transitions
  • Side effects: Methods trigger notifications, logging
  • Encapsulation: Internal state is hidden behind public methods

Summary: Use a Class When

  • You need mutable state / setters
  • The object contains substantial behavior
  • Inheritance hierarchy is required
  • It's a JPA entity (@Entity)

Mental Model

Putting It All Together

Each concept serves a distinct purpose. Here's how they fit together.

Mental Model — Record + Builder + Compact Constructor

record

Defines what data the object contains. All components are final. Auto-generates constructor, accessors, equals, hashCode, toString.

@Builder

Defines how callers create the object. Fluent, readable API. Avoids telescoping constructors. Works on both classes and records.

Compact Constructor

Handles validation and normalization during construction. Runs before the object is created. Perfect for null-safe defaults like List.of().

For your AuditPublishRequest: The record is a good fit because it is an immutable request/data object. A class would also work, but would add boilerplate unless you need class-specific behavior or mutability.

List.of() — Immutable Empty List

The compact constructor uses List.of() to return an immutable empty list when changes is null:

// null → List.of() → []
changes = changes == null ? List.of() : changes;

// List.of() returns an IMMUTABLE list
// callers cannot add/remove elements — safe by design
