The Blueprint

Every Spring Boot app you'll ever touch is the same four rooms, wired the same way.

The analogy

Picture the app as an office with one strict rule: nobody outside the building touches the warehouse directly. A visitor (the client) hands their request to the receptionist (Controller). The receptionist doesn't make judgment calls — they pass it straight to the manager (Service), who applies the actual business rules and decides what needs to happen. If a trip to the shelves is required, the manager sends the warehouse clerk (Repository) — the only person in the building allowed to touch the database.

FIG 1.1 — the request/response path, and what language each hop speaks

The rule worth tattooing on your forearm: Controllers speak DTO. Repositories speak Entity. The Service layer is the translator standing between them. A DTO (Data Transfer Object) is a plain shape built for the outside world — only the fields a client should see, in whatever format the API contract promises. An Entity is a plain shape built for the database — it mirrors a table, carries JPA annotations, and knows nothing about HTTP.

Keep those two worlds apart and you get a real benefit, not just tidiness: you can rename a database column, split a table, or add an internal-only field, and as long as the Service still produces the same DTO shape, nothing about your public API breaks. The reverse is true too — you can reshape the API response without touching your schema.

// StudentController.java @RestController @RequestMapping("/students") public class StudentController { @Autowired private StudentService studentService; @PostMapping public ResponseEntity<StudentDto> createNewStudent( @RequestBody @Valid AddStudentRequestDto dto) { // Controller never sees a Student entity — only DTOs in, DTOs out. return ResponseEntity.status(HttpStatus.CREATED) .body(studentService.createNewStudent(dto)); } } // StudentServiceImpl.java @Service public class StudentServiceImpl implements StudentService { @Autowired private StudentRepository studentRepository; public StudentDto createNewStudent(AddStudentRequestDto dto) { Student entity = mapToEntity(dto); // DTO -> Entity Student saved = studentRepository.save(entity); return mapToDto(saved); // Entity -> DTO } }
Field note

Why not skip the DTO and just return the Entity? Three reasons it bites people: (1) Hibernate proxies and lazy-loaded associations don't serialize to JSON cleanly and can throw at render time; (2) your Entity may carry fields — password hashes, internal flags, audit columns — that were never meant to leave the building; (3) your public API contract becomes hostage to your table schema, so a routine migration turns into a breaking change for every client.

Blueprint check — a discount now depends on how many previous orders a customer has. Which layer do you open first?

The Service layer. That's a business rule, not routing (Controller's job) and not a raw data read (Repository's job). The Controller and Repository shouldn't need to change at all.

Anatomy of a Request

Your controller method is the sixth thing that happens, not the first.

The analogy

Every request that hits your app lands at a control tower before it ever reaches your code. That's the DispatcherServlet — Spring's front controller. It runs no business logic and doesn't know what a "Student" is. Its only job is traffic control: catch the incoming plane, work out which gate it belongs to, have ground crew guide it in, and once your code hands back a package, repackage it in the format the runway expects before sending it back out.

FIG 2.1 — one request's round trip, top to bottom

Two hops are worth slowing down on. HandlerMapping is purely a lookup: it scans every @RequestMapping/@GetMapping/etc. registered at startup and finds the one whose path and HTTP method match. HandlerAdapter is what actually invokes that method — resolving @PathVariable, @RequestBody, and @RequestParam arguments before calling it. Your controller method is step six. Everything before it is Spring deciding whether and how to call you at all.

Field note

This is also why a Spring Boot jar can be java -jar app.jar with no separate install step: Tomcat isn't a server you deploy to, it's a library embedded inside your application, started by SpringApplication.run().

Common gotcha

404 vs 406, and what they actually tell you. A 404 means HandlerMapping never found a match — check the URL path, the HTTP method, and that your controller class is actually component-scanned. A 406 Not Acceptable means a handler was found and ran fine, but no HttpMessageConverter could produce the format the client's Accept header asked for. Same pipeline, two very different stages failing.

Blueprint check — Postman returns 404 for a URL you're sure exists in your controller. Which stage is failing?

HandlerMapping. It never matched your URL pattern to a registered handler — the request never even reached HandlerAdapter, let alone your method. Double-check the path, the HTTP verb, and that the controller's package is under component scan.

The Repository Toolbox

Four interfaces, each one clipping more tools onto the last.

The analogy

Repository<T,ID> is an empty toolbox with a label on it — a marker interface Spring uses to recognize "this is a data-access contract," with nothing inside. CrudRepository adds the basic hand tools: save(), delete(), findById(). PagingAndSortingRepository clips a page-and-sort attachment onto that same box. QueryByExampleExecutor is a separate accessory that lets you hand it a half-filled-in object and get matches back. JpaRepository is the contractor's full chest — it inherits everything from the attachments and throws in a few JPA-only extras.

FIG 3.1 — what extends what (QueryByExampleExecutor joins independently, not through CrudRepository)
InterfaceAddsA few signature methods
Repository<T,ID>nothing — just a marker Spring recognizes(empty)
CrudRepository<T,ID>basic CRUDsave(S), findById(ID), findAll(), deleteById(ID), count(), existsById(ID)
PagingAndSortingRepository<T,ID>pagination & sortingfindAll(Pageable), findAll(Sort)
QueryByExampleExecutor<T>query-by-examplefindAll(Example<S>), findOne(Example<S>)
JpaRepository<T,ID>everything above, plus JPA extrasflush(), saveAndFlush(S), deleteAllInBatch(), getReferenceById(ID)
Field note

Which one do you actually extend? Ninety-nine times out of a hundred: JpaRepository<Entity, ID>. You get everything without thinking about it. Dropping down to plain CrudRepository is a deliberate design-purity move — usually to stop a particular repository from exposing pagination or batch deletes at all.

Common gotcha

getOne(ID) is deprecated in modern Spring Data JPA in favor of getReferenceById(ID) — both return a lazy proxy without hitting the database, which is different from findById(ID), which queries immediately and returns an Optional. Reach for the reference version only when you need to set a foreign key and don't actually need the row's data.

Blueprint check — your interface extends only CrudRepository, and you call findAll(PageRequest.of(0, 20)). Compiles?

No. findAll(Pageable) lives on PagingAndSortingRepository, not CrudRepository. Either extend JpaRepository instead, or add PagingAndSortingRepository to the interface's extends list.

The Life of an Entity

Four states. Once you can name which one you're in, half of Hibernate's "mystery" bugs stop being mysteries.

The analogy

An entity's life reads like a paper form moving through a government office. Fresh off your printer it's just paper — Transient — nobody in the building knows it exists. File it at the front desk and it becomes Persistent: it's in the tracking system now, and anything you scribble on it later gets synced automatically. Photocopy it and walk out with your copy, and that copy is Detached — same data, but the office stopped watching it. Mark the original "VOID — SHRED" and it's Removed: still sitting in the outbox, waiting for the shredder.

FIG 4.1 — the four states every entity moves through, and the calls that move it
EntityManager em = /* injected */; Patient p1 = new Patient(); // TRANSIENT — just a Java object p1.setName("Asha"); em.persist(p1); // TRANSIENT -> PERSISTENT (INSERT queued) p1.setAge(31); // no explicit save() call needed — // dirty checking syncs this at flush/commit em.detach(p1); // PERSISTENT -> DETACHED (no longer tracked) p1.setAge(45); // this change never reaches the database Patient managed = em.merge(p1); // DETACHED -> PERSISTENT (a *new* managed copy!) em.remove(managed); // PERSISTENT -> REMOVED (DELETE queued)
Field note

You'll meet three overlapping vocabularies for the same four states, and it's worth knowing which one you're reading. Hibernate's native Session API uses save() / update() / saveOrUpdate() / delete(). The JPA standard (EntityManager, which Hibernate also implements) uses persist() / merge() / remove(). Spring Data's JpaRepository.save() is a third thing entirely — a convenience wrapper that decides between persist() and merge() internally, based on whether the entity's ID field is null.

Common gotcha

Dirty checking only works on a managed (Persistent) entity. Detach it, mutate it, and nothing complains — no exception, no warning — the change simply never reaches the database. This is the classic "I definitely set that field, why didn't it save?" bug, usually caused by mutating an entity after the transaction (and its PersistenceContext) has already closed.

Blueprint check — you call em.detach(patient), then patient.setName("New Name"). Does the database get updated?

No. Once detached, the entity is no longer tracked by any PersistenceContext, so dirty checking has nothing to compare against. You'd need to call em.merge(patient) to get a managed copy back before the change can be persisted.

The Session's Notebook

Why asking for the same row twice doesn't mean two trips to the database.

The analogy

The PersistenceContext is the EntityManager's short-term memory for the current session. Ask it for the same entity twice inside one transaction, and the second time it checks its own notepad before ever bothering the database. This isn't opt-in caching — it's simply how every managed entity behaves for as long as its transaction is open.

FIG 5.1 — a persist() and a find() within the same PersistenceContext

The PersistenceContext is often called the first-level cache, and it's scoped to one EntityManager — which, inside a @Transactional Spring method, means it's scoped to one transaction. Every managed entity you touch during that transaction is registered here, along with a snapshot of its field values at load time. At flush (usually just before commit), Hibernate compares each managed entity against its snapshot and issues UPDATE statements only for the ones that actually changed — this comparison is what people mean by "dirty checking."

Field note

A fact that surprises people the first time: call find() for the same ID twice inside one PersistenceContext, and you don't just get two equal objects — you get the exact same object reference. a == b is true, not just a.equals(b). That's a direct consequence of the cache: the second call never leaves the notebook.

Blueprint check — inside one transaction, you call studentRepository.findById(5) twice. How many SELECTs hit the database?

One. The first call queries the database and registers the entity in the PersistenceContext. The second call finds it already sitting in the notebook and returns it directly — no second trip.

Sheet 06 / 08

All or Nothing

A transaction is a pact: every query in the block lands, or none of them do.

The analogy

Moving money from Account A to Account B is two writes: subtract here, add there. If the second write fails after the first one already landed, money quietly vanishes — unless something guarantees both happen together or neither does. That guarantee is a transaction.

FIG 6.1 — a transaction is a single unit: it succeeds whole or fails whole
@Transactional public void transferBalance(Long fromId, Long toId, BigDecimal amount) { Account from = accountRepository.findById(fromId).orElseThrow(); Account to = accountRepository.findById(toId).orElseThrow(); from.setBalance(from.getBalance().subtract(amount)); to.setBalance(to.getBalance().add(amount)); // if this throws, BOTH balance changes above are rolled back too — // Hibernate typically defers UPDATEs to flush time, right before commit if (to.getBalance().compareTo(BigDecimal.ZERO) < 0) { throw new IllegalStateException("insufficient funds"); } }
Field note

By default, @Transactional rolls back on unchecked exceptions (anything extending RuntimeException) but not on checked exceptions. If your method throws a checked exception and you still need a rollback, say so explicitly: @Transactional(rollbackFor = Exception.class).

Common gotcha — the self-invocation trap

@Transactional works through a Spring-generated proxy wrapped around your bean. Call a transactional method from another method in the same class (this.someMethod()) and you bypass that proxy entirely — the call never goes through the interceptor, so no transaction opens, silently. This is one of the most common "why isn't my transaction working" bugs in Spring.

Blueprint check — methodA() (no @Transactional) calls this.methodB() (@Transactional), same class. Does methodB run inside a transaction?

No. The internal call bypasses Spring's proxy, so the @Transactional annotation on methodB is silently ignored. To fix it, either call methodB through a separately injected bean, or move it to another Spring-managed class.

The Domino Effect

Cascading decides whether an operation on the parent ripples down to its children — or stops at the front door.

The analogy

Think of a parent entity and its children as a family heading out the door. Cascading is the house rule that decides whether the kids come along automatically, or stay behind unless someone fetches them separately. Save the parent with the right cascade setting, and the children get saved in the same trip. Delete the parent without that setting, and the children are left standing on the porch — often triggering a foreign-key error, since they still point at a parent that no longer exists.

FIG 7.1 — one Order, three OrderItems, wired with cascade = ALL
CascadeTypeWhen you ___ the parent…this also happens to the children
PERSISTsave a new parentnew children get saved too
MERGEmerge a detached parenttheir detached children get merged too
REMOVEdelete the parentchildren get deleted too
REFRESHrefresh the parent from the DBchildren get refreshed too
DETACHdetach the parentchildren get detached too
ALLany of the aboveevery row above applies
@Entity public class Order { @Id @GeneratedValue private Long id; @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true) private List<OrderItem> items = new ArrayList<>(); }
Field note — orphanRemoval is not CascadeType.REMOVE

They sound similar and get confused constantly. CascadeType.REMOVE fires only when you explicitly delete the parent — orderRepository.delete(order) — and every child goes with it. orphanRemoval = true fires on a narrower, different trigger: pulling a child out of the parent's in-memory collection, order.getItems().remove(someItem), even while the Order itself lives on. That "orphaned" item gets deleted from the database at the next flush — no explicit delete call needed.

Common gotcha

Cascade is an application-level concept — it only fires through EntityManager operations. It's a different mechanism from a database's own ON DELETE CASCADE foreign key constraint, which fires at the database layer regardless of whether Hibernate is even involved. And be careful putting CascadeType.ALL on both sides of a bidirectional relationship — cascade should almost always live only on the side that "owns" the lifecycle (parent → children), or you risk a child's save accidentally cascading back up and touching a parent shared by other records.

Blueprint check — Order has cascade = CascadeType.PERSIST only (no REMOVE). You call orderRepository.delete(order). What happens to its OrderItems?

They are not cascade-deleted. Only PERSIST was configured, so Hibernate makes no attempt to remove the children. In practice, since the child rows still hold a foreign key pointing at the now-deleted Order, you'll typically get a foreign-key constraint violation rather than a clean delete — a strong hint that REMOVE (or ALL) was missing.

Wiring It All Together

One POST request, start to finish, with every earlier sheet doing its part.

FIG 8.1 — the whole pipeline, condensed

Take a POST to /students from the top:

Blueprint check — a teammate adds a repository call directly inside the Controller, skipping the Service. Name two rules from this set they just broke.

First, the layering rule from Sheet 1: the Controller now speaks Entity instead of DTO, coupling the public API directly to the database schema. Second, that call happens outside any @Transactional boundary, so if the returned entity has lazy associations accessed later — say, while Jackson serializes it — there's a real risk of a LazyInitializationException, because the PersistenceContext that could have loaded them has already closed (Sheets 5 & 6).
