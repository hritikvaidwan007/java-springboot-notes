Core Concept

What is an ER Diagram?

An Entity-Relationship Diagram describes business entities, their attributes, and the relationships between them. It is the blueprint for your database schema. The core mental model: ERD describes business relationships; PKs, FKs, and constraints implement them; JPA maps that schema into Java objects.

Entity

A real-world object or concept — becomes a table in the database and an @Entity class in JPA.

Examples: PATIENT, DOCTOR, APPOINTMENT

Attribute

A property of an entity — becomes a column in the table.

Examples: name, email, insurance_id

Relationship

An association between entities — implemented via foreign keys or junction tables.

Examples: books, handles, assigned_to

JPA Owning vs Inverse Side

Use the foreign key location to decide which side owns a relationship in JPA. The side with the FK is normally the owning side because it controls the database relationship.

JPA Implementation

Complete JPA Entity Code

Patient.java (Owning: 1:1 with Insurance)

@Entity
@Table(name = "patient")
public class Patient {

  @Id
  @GeneratedValue(strategy =
    GenerationType.IDENTITY)
  private Long id;

  @Column(nullable = false, length = 100)
  private String name;

  @Column(unique = true)
  private String email;

  // ── 1:1 with Insurance (OWNING SIDE)
  @OneToOne
  @JoinColumn(name = "insurance_id",
    unique = true)
  private Insurance insurance;

  // ── 1:N with Appointment (INVERSE)
  @OneToMany(mappedBy = "patient")
  private List<Appointment> appointments;
}

Insurance.java (Inverse: 1:1 with Patient)

@Entity
@Table(name = "insurance")
public class Insurance {

  @Id
  @GeneratedValue(strategy =
    GenerationType.IDENTITY)
  private Long id;

  private String policyNumber;
  private String provider;
  private String coverageType;

  // ── 1:1 (INVERSE SIDE)
  @OneToOne(mappedBy = "insurance")
  private Patient patient;
}

Appointment.java (Owning: two N:1)

@Entity
@Table(name = "appointment")
public class Appointment {

  @Id
  @GeneratedValue(strategy =
    GenerationType.IDENTITY)
  private Long id;

  @Column(nullable = false)
  private LocalDateTime appointmentDate;

  @Enumerated(EnumType.STRING)
  private AppointmentStatus status;

  // ── N:1 with Patient (OWNING SIDE)
  @ManyToOne(optional = false)
  @JoinColumn(name = "patient_id",
    nullable = false)
  private Patient patient;

  // ── N:1 with Doctor (OWNING SIDE)
  @ManyToOne(optional = false)
  @JoinColumn(name = "doctor_id",
    nullable = false)
  private Doctor doctor;
}

Doctor.java & Department.java (M:N)

// ── Doctor.java ──
@Entity
public class Doctor {
  @Id
  @GeneratedValue(strategy =
    GenerationType.IDENTITY)
  private Long id;
  private String name;
  private String specialization;

  // M:N — owns via @JoinTable
  @ManyToMany
  @JoinTable(
    name = "doctor_department",
    joinColumns = @JoinColumn(
      name = "doctor_id"),
    inverseJoinColumns = @JoinColumn(
      name = "department_id"))
  private Set<Department> departments;

  // 1:N Inverse (appointments)
  @OneToMany(mappedBy = "doctor")
  private List<Appointment> appointments;
}

// ── Department.java ──
@Entity
public class Department {
  @Id
  @GeneratedValue(strategy =
    GenerationType.IDENTITY)
  private Long id;
  private String name;

  // M:N Inverse
  @ManyToMany(mappedBy = "departments")
  private Set<Doctor> doctors;

  // N:1 to head doctor (OWNING)
  @ManyToOne
  @JoinColumn(name = "head_doctor_id")
  private Doctor headDoctor;
}
Tip: If the M:N junction table has extra attributes (e.g., assignment_date, role), prefer an explicit entity (e.g., DoctorDepartment with its own @Id) instead of a bare @ManyToMany.

Relationship Type

Identifying vs Non-Identifying Relationships

Non-Identifying

Child has its own independent PK; parent PK is only an FK.

APPOINTMENT(
  id            ← own PK,
  appointment_date,
  patient_id    ← FK only, not part of PK,
  doctor_id     ← FK only
)

This is the most common pattern. The child can exist with a separate identity.

Identifying

Child PK includes parent PK; child identity depends on parent.

ORDER_ITEM(
  order_id      ← part of composite PK,
  product_id    ← part of composite PK,
  quantity,
  unit_price
)

The child cannot exist without the parent. Used in parent-child dependencies.

Entity Strength

Strong vs Weak Entity

Strong Entity

  • Has its own primary key
  • Can be uniquely identified independently
  • Represented with a single rectangle in ERD

Examples: PATIENT, DOCTOR, DEPARTMENT

Weak Entity

  • Depends on another entity for identification/existence
  • Owner's key often forms part of its PK
  • Represented with a double rectangle in ERD
  • Has an identifying relationship (double diamond)

Examples: ORDER_ITEM depends on ORDER, PRESCRIPTION_DETAIL depends on PRESCRIPTION

Advanced Modeling

Relationship Attributes

When a relationship itself carries attributes, model it as an associative entity.

STUDENT — ENROLLMENT — COURSE (Associative Entity)

The relationship attributes (enrollment_date, grade) belong to the association itself — they cannot live on STUDENT or COURSE alone. The associative entity ENROLLMENT has a composite PK of (student_id, course_id).

Self-Reference

Recursive / Self-Referencing Relationship

An entity can relate to itself. Example: one manager manages many employees; an employee may have zero or one manager.

ERD Representation

EMPLOYEE ←──────────→ EMPLOYEE
     manager_id → id

One manager manages many employees.
An employee has 0 or 1 manager.

JPA Implementation

@Entity
public class Employee {
  @Id
  @GeneratedValue
  private Long id;
  private String name;

  // Self-referencing N:1
  @ManyToOne
  @JoinColumn(name = "manager_id")
  private Employee manager;

  // Self-referencing 1:N
  @OneToMany(mappedBy = "manager")
  private List<Employee> subordinates;
}
N-ary Relationships

Ternary / N-ary Relationship

A relationship involving 3 or more entities. Example: a supplier supplies a product to a specific warehouse.

ERD

SUPPLIER ───┐
PRODUCT  ───┤── SUPPLY ── quantity
WAREHOUSE ──┘

Three entities connected by a single diamond (ternary relationship).

Relational Implementation

SUPPLY(
  supplier_id  → SUPPLIER,
  product_id   → PRODUCT,
  warehouse_id → WAREHOUSE,
  quantity,
  PRIMARY KEY(supplier_id,
    product_id, warehouse_id)
)

Optionality

Nullability & Mandatory Relationships

Optional Relationship

  • Minimum cardinality = 0
  • FK is often nullable
  • Example: department.head_doctor_id NULL — no head assigned yet

Mandatory Relationship

  • Minimum cardinality = 1
  • FK is often NOT NULL
  • Example: appointment.doctor_id NOT NULL — every appointment requires a doctor

Normalization

Database Normalization

Practical goal: store each fact in the appropriate place and reduce unnecessary duplication.

1NF — First Normal Form

  • Atomic values (no multi-valued columns)
  • No repeating groups
  • Each cell holds a single value

Bad: phones: "123, 456"
Good: separate rows or table

2NF — Second Normal Form

  • Must be in 1NF
  • No partial dependency on part of a composite key
  • Every non-key column depends on the entire PK

Only relevant when composite PK exists

3NF — Third Normal Form

  • Must be in 2NF
  • No transitive dependency of non-key attributes on the key
  • Non-key columns depend only on the PK, not on other non-key columns

Bad: patient → zip → city (transitive)
Good: separate address table

Referential Actions

Delete / Update Actions

ActionMeaningWhen to Use
CASCADEPropagate parent change to dependent rowsParent-child ownership (e.g., ORDER → ORDER_ITEM)
SET NULLSet child FK to NULLOptional relationship (e.g., department head leaving)
RESTRICT / NO ACTIONPrevent operation when dependents existSafety default; prevents accidental data loss

Warning: Use CASCADE carefully — cascading deletes can remove many dependent rows. Prefer RESTRICT in production and handle deletion logic in application code.

// CascadeType.ALL       — all of the above
Skill

How to Read an ERD — Step by Step

7-Step Reading Process

  • 1. Find every entity/table and list them
  • 2. Find every foreign key
  • 3. Read cardinality at both ends (1, *, 0..1)
  • 4. Classify each relationship as 1:1, 1:N, or M:N
  • 5. For M:N — locate the junction table
  • 6. Check optionality: 0 = optional, 1 = mandatory
  • 7. Look for relationship attributes needing an associative entity

JPA-Specific Steps

  • 8. Identify which side has @JoinColumn (owning side)
  • 9. Identify which side uses mappedBy (inverse side)
  • 10. Check cascade types and orphan removal settings
  • 11. Check fetch types (LAZY vs EAGER)
  • 12. Verify @Enumerated for status/type fields
  • 13. Look for inheritance mapping strategies
  • 14. Check @Version for optimistic locking
Pitfalls

Common Mistakes

FK Mistakes

  • FK on wrong side of 1:N (should be on N side)
  • Assuming FK alone means 1:1 (need UNIQUE too)
  • Ignoring NULL/NOT NULL when modeling optionality

JPA Mistakes

  • Making both sides the owner (only one owns)
  • Confusing mappedBy with a DB column name (it's a Java field name)
  • Using @ManyToMany when junction table has meaningful attributes

Design Mistakes

  • Confusing 0..* with 1..* (optionality matters)
  • Not modeling relationship attributes as entities
  • Over-normalizing or under-normalizing
